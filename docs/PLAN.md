# net-lib-01: план разработки (v2)

Здесь собраны критерии и план. Код начнём писать после аппрува.
По сравнению с v1 учтены ответы на открытые вопросы и новые требования: упаковка MTU и приоритеты.

## 1. Цель и границы

Транспортная библиотека на Rust поверх UDP для fast-paced FPS. По функциям ориентируемся на LiteNetLib 1.x.
Библиотека ничего не знает о Unity. Unity для неё такой же потребитель, как консольное .NET-приложение.

**В scope:**

- соединения;
- режимы доставки Reliable и Unreliable со всеми вариантами;
- максимальная упаковка MTU-пакетов;
- приоритизация отправки;
- фрагментация;
- ack, RTT;
- миграция соединения;
- опциональное шифрование;
- C ABI и .NET-биндинг.

**Вне scope** (это делает игровой проект или это не нужно):

- снапшоты, дельта-компрессия, синхронизация тиков, prediction, lag compensation;
- NAT punch-through, LAN discovery.

**Параметры нагрузки:** сервер до 64 игроков, tick rate 64 Гц.

**Целевые платформы:** Linux server (x86_64, aarch64), Windows client (x86_64), Android (arm64-v8a, armeabi-v7a, x86_64), iOS (arm64, staticlib), macOS (universal: arm64 + x86_64).

**Unity 6** (6000.x), IL2CPP и Mono, .NET Standard 2.1. **Лицензия** MIT OR Apache-2.0.

## 2. Модель отправки

### 2.1 Режимы доставки

| Режим | Гарантии | Типичное использование |
|-------|----------|------------------------|
| `Unreliable` | без гарантий | эффекты, звуки |
| `UnreliableSequenced` | старые и дубли отбрасываются | позиции и повороты игроков, ввод |
| `ReliableUnordered` | доставка гарантирована, порядок нет | загрузка ресурсов, независимые события |
| `ReliableOrdered` | доставка и порядок | чат, RPC, игровые события |
| `ReliableSequenced` | гарантирована доставка последнего, промежуточные можно пропустить | состояние «последнее значение» (счёт, настройки) |

Каналы задаются при создании менеджера: `ChannelConfig { id, mode, priority, ttl }`.
Число каналов до 16, номер канала занимает 4 бита в байте заголовка сообщения.

### 2.2 Упаковка MTU

- `send()` ничего не отправляет в сеть, а только кладёт сообщение в очередь пира.
  Сборка датаграмм происходит в `flush()`: явно в конце тика или автоматически в `poll()`.
  Таймерной задержки как в Nagle нет, поэтому лишней латентности тоже нет.
- Сборщик заполняет каждую датаграмму до `MTU − header`. В один пакет идут все каналы сразу: новые сообщения, ретрансмиты reliable и piggyback-ack.
- Большие сообщения режутся на фрагменты. Размер фрагмента подстраивается под свободное место в текущем пакете, поэтому фрагмент «дозаполняет» пакет.
- Сообщение без пары внутри датаграммы не платит за поле длины: длину даёт размер датаграммы.
- Если входящего трафика нет, ack уходит отдельным минимальным пакетом не чаще раза в N мс. При встречном трафике ack только piggyback.

### 2.3 Приоритеты

- У канала есть базовый приоритет (`u8`). Его можно переопределить на конкретном сообщении: `send_with(priority, …)`.
- У пира есть **бюджет полосы** (байт/с, настраивается, по умолчанию без лимита) и бюджет на тик.
  `flush()` берёт данные в порядке убывания **эффективного приоритета**, пока не исчерпаны место и бюджет.
- **Защита от голодания:** у ожидающих сообщений копится приоритет со временем (priority accumulator, как в Unreal Engine и у Glenn Fiedler). Поэтому низкий приоритет гарантированно уходит за ограниченное время.
- **TTL для unreliable:** устаревшее сообщение (например позиция из прошлого тика) выбрасывается из очереди и не тратит полосу.
  Для `UnreliableSequenced` есть опция «replace latest»: новое сообщение заменяет неотправленное старое в той же очереди.
- Ретрансмиты reliable наследуют приоритет канала. У служебных пакетов (handshake, ack, ping) приоритет наивысший.

### 2.4 Миграция соединения (минимум дисконнектов)

- В steady state миграция стоит **0 байт**: пир идентифицируется по адресу.
- Если сервер получает пакет с незнакомого адреса, он отвечает коротким stateless-запросом «назовись». Ответ не больше входящего пакета, так что амплификации нет.
  Клиент также проактивно отправляет migration-заголовок после паузы во входящем трафике или после пересоздания сокета.
- Migration-заголовок: `conn_id` (u32) + `token` (8 байт, keyed hash от секрета handshake и seq).
  Сервер проверяет токен и path challenge на новый адрес. До подтверждения адреса сервер отправляет на него не больше 3× от полученного (как в QUIC). После этого пир перепривязывается, очереди reliable сохраняются.
- Драйвер на клиенте сам пересоздаёт сокет при ошибках: iOS и Android закрывают сокеты в background, бывает смена интерфейса.
- Таймаут дисконнекта настраивается, по умолчанию 10 с. Сетевые «дыры» короче таймаута не рвут сессию, а после восстановления очереди догоняются.

## 3. Критерии приёмки

У каждого критерия есть способ проверки. Пороговые значения стартовые.

### 3.1 Трафик

| ID | Критерий | Цель | Как проверяем |
|----|----------|------|---------------|
| B1 | Заголовок unreliable-пакета | ≤ 3 байта | unit-тест |
| B2 | Заголовок с piggyback-ack (seq + ack + битмаска) | ≤ 8 байт | unit-тест |
| B3 | Накладные байты на сообщение в склеенном пакете (unreliable) | 1 байт при длине < 64, иначе 2; reliable +2 байта (msg seq) | unit + property-тест |
| B4 | При встречном трафике 64 Гц отдельных ack-пакетов нет | 0 | счётчик в симуляторе |
| B5 | Сравнение с LiteNetLib на одинаковом сценарии | меньше байт на проводе | сравнительный бенч |
| B6 | Шифрование выключено (по умолчанию) | 0 байт overhead | unit-тест |
| B7 | Шифрование включено | ≤ 24 байта на пакет | unit-тест |

### 3.2 Упаковка MTU

| ID | Критерий | Цель | Как проверяем |
|----|----------|------|---------------|
| PK1 | Число датаграмм за `flush()` | ≤ ⌈Σ(payload+overhead) / capacity⌉ + 1 | property-тест на случайных наборах сообщений |
| PK2 | Заполненность всех датаграмм, кроме последней | ≥ 95 % от MTU | property-тест + `bandwidth_report` |
| PK3 | Ретрансмиты, новые данные и ack разных каналов делят пакет | да | сценарный тест |
| PK4 | Фрагменты дозаполняют пакет; сборка работает при потере фрагментов | да | тест с потерями |
| PK5 | `send()` + `flush()` не аллоцируют в steady state | 0 alloc | counting allocator |

### 3.3 Приоритеты

| ID | Критерий | Как проверяем |
|----|----------|---------------|
| PR1 | При ограниченном бюджете сообщения высокого приоритета уходят в текущем `flush()`, если помещаются | тест: бюджет 50 %, проверка состава пакетов |
| PR2 | Защита от голодания: сообщение с низким приоритетом уходит не позже чем через T_max (настраивается) при любой нагрузке выше приоритетом | property-тест |
| PR3 | Сообщения с истёкшим TTL не отправляются, «replace latest» заменяет устаревшее | unit-тест |
| PR4 | Бюджет полосы соблюдается с точностью ±5 % на окне 1 с | симулятор |
| PR5 | Стоимость планировщика | ≤ O(n log k) на `flush()`, n — сообщений, k — уровней | бенч |

### 3.4 Надёжность и корректность

| ID | Критерий | Как проверяем |
|----|----------|---------------|
| R1 | Все 5 режимов доставки соответствуют контракту (2.1) | сценарные тесты |
| R2 | Корректность при 0–20 % потерь, 0–300 мс задержки, ±50 мс джиттера, дублях и reorder | proptest через эмулятор, тысячи seed'ов |
| R3 | Wraparound номеров последовательности (u16) | тест на 200k+ пакетов |
| R4 | RTO по RFC 6298 (SRTT/RTTVAR), без лавины ретрансмитов | метрики симулятора |
| R5 | Таймауты, keepalive, disconnect с причиной | сценарные тесты |
| R6 | Детерминизм: один seed даёт одинаковый результат | тест-повтор |

### 3.5 Миграция и мобильная устойчивость

| ID | Критерий | Как проверяем |
|----|----------|---------------|
| M1 | Смена адреса клиента (NAT rebinding, Wi-Fi ↔ LTE) без дисконнекта, reliable-данные не теряются | симулятор: смена адреса посреди reliable-потока |
| M2 | Пересоздание сокета клиента (уход в background и возврат) без дисконнекта, если пауза < таймаута | сценарный тест + ручная проверка на iOS и Android |
| M3 | Перехватить соединение без токена невозможно; поддельный токен игнорируется | тест + fuzz |
| M4 | На неподтверждённый адрес уходит ≤ 3× полученного | тест |
| M5 | Время восстановления после смены адреса | ≤ 1 RTT + 1 тик |

## 4. Архитектура

```
crates/
  netlib-core   # sans-IO: соединения, каналы, планировщик (приоритеты + упаковка), ack, фрагментация, миграция, формат провода
  netlib        # std-драйвер: non-blocking UdpSocket, пересоздание сокета, Manager::poll()/flush()
  netlib-sim    # сетевой эмулятор: потери, задержка, джиттер, дубли, reorder, лимит полосы, смена адреса
  netlib-ffi    # C ABI (cdylib + staticlib), cbindgen
bindings/dotnet # NetLib (.NET Standard 2.1), P/Invoke, Span-API, без Unity
examples/       # echo-сервер, консольный клиент, нагрузочный бот (64 клиента)
unity-sample/   # Unity 6 проект — только потребитель
fuzz/           # цели cargo-fuzz
xtask/          # cargo xtask report|build-all|bindings
```

- **Sans-IO ядро.** В ядро передаются байты и время, оно возвращает датаграммы и события. Тесты детерминированные.
- **Poll и flush.** Колбэков из нативного кода и фоновых потоков нет. Игра вызывает `poll()` в начале тика и `flush()` в конце.
- **Формат провода** (черновик, финализируется в M0):
  - пакет: `[type+flags 1 байт][seq u16][ack u16 + битмаска, если флаг]`;
  - сообщение: `[channel 4 бита + flags 4 бита][len varint, если сообщение не последнее][msg_seq u16, если reliable][fragment info, если фрагмент][payload]`.
- **MTU** по умолчанию 1200.

## 5. Как работаем интерактивно

Каждая веха устроена одинаково:

1. Короткий дизайн-апдейт.
2. Реализация.
3. Отчёт `cargo xtask report`: таблица критериев вехи с отметкой ✅/❌ и цифрами.
4. Демо-команда, которую можно запустить самому.
5. **Гейт аппрува.**

| Веха | Содержимое | Критерии | Демо |
|------|------------|----------|------|
| **M0** | `WIRE_FORMAT.md` v0, финализация API-эскиза | Q2 | документ |
| **M1** | Workspace, CI, sans-IO ядро: handshake с challenge, keepalive, timeout, disconnect; симулятор; std-драйвер | R5, R6, S1, S2, Q1 | echo на localhost; симулятор с потерями |
| **M2** | Каналы и 5 режимов доставки, ack, RTO, фрагментация | R1–R4, B1–B4 | `sim --loss 20 --latency 100` |
| **M3** | Планировщик: упаковка MTU, приоритеты, бюджет, aging, TTL / replace-latest, zero-alloc | PK1–PK5, PR1–PR5, P1 | отчёт: заполненность пакетов и задержки по приоритетам при урезанной полосе |
| **M4** | Миграция соединения, пересоздание сокета | M1–M5 | `sim --rebind-every 5s` без дисконнектов |
