# net-lib-01: план разработки

Здесь собраны критерии и план. Код начнём писать после аппрува.

## 1. Цель

Библиотека на Rust поверх UDP для синхронизации клиента и сервера в fast-paced FPS.
По функциям ориентируемся на LiteNetLib 1.x: соединения, каналы доставки, ack, фрагментация, склейка сообщений, ping/RTT, MTU.
Отличаемся тремя вещами:

- накладные байты на пакет и на сообщение меньше, чем у LiteNetLib;
- ядро без I/O (sans-IO), поэтому его можно детерминированно тестировать;
- есть C ABI и отдельный .NET-биндинг, через который библиотека подключается к Unity.

Unity при этом библиотека не знает. Unity для неё такой же потребитель, как консольное .NET-приложение.

Целевые платформы: Linux server (x86_64, aarch64), Windows client (x86_64), Android (arm64-v8a, armeabi-v7a, x86_64), iOS (arm64, статическая линковка), macOS (universal: arm64 + x86_64).

## 2. Критерии приёмки

У каждого критерия есть способ проверки. Пороговые значения стартовые, их можно поправить при аппруве.

### 2.1 Трафик (главный критерий)

| ID | Критерий | Цель | Как проверяем |
|----|----------|------|---------------|
| B1 | Заголовок пакета, в котором только unreliable-данные | ≤ 3 байта | unit-тест на размер сериализации |
| B2 | Заголовок пакета с piggyback-ack (seq + ack + ack-битмаска) | ≤ 8 байт | unit-тест |
| B3 | Накладные байты на сообщение внутри склеенного пакета | 1 байт при длине < 128, иначе 2 | unit-тест + property-тест |
| B4 | Полезная нагрузка при MTU 1200 и 20 сообщениях по 40 байт | ≥ 95 % от UDP payload | бенч-отчёт `bandwidth_report` |
| B5 | Нет отдельных ack-пакетов, если есть встречный трафик | 0 standalone-ack при симметричном трафике 30+ Гц | счётчик в симуляторе |
| B6 | Bit-packing: квантованные float, quaternion в формате smallest-three, varint/zigzag, дельта | например позиция ≤ 6 байт, поворот ≤ 4 байта | unit-тесты + бенч |
| B7 | Сравнение с LiteNetLib на одинаковом сценарии | у нас меньше байт на проводе | сравнительный бенч (C# LiteNetLib vs наш биндинг) |

### 2.2 Надёжность и корректность

| ID | Критерий | Как проверяем |
|----|----------|---------------|
| R1 | Режимы доставки Unreliable, Sequenced, ReliableUnordered, ReliableOrdered и ReliableSequenced работают по контракту | сценарные тесты в симуляторе |
| R2 | Корректная работа при 0–20 % потерь, 0–300 мс задержки, ±50 мс джиттера, дублях и переупорядочивании | property-тесты (proptest) через сетевой эмулятор, тысячи seed'ов |
| R3 | Wraparound номеров последовательности (u16) | тест на 200k+ пакетов |
| R4 | Фрагментация и сборка reliable-сообщений больше MTU (до N КБ) | тесты с потерей фрагментов |
| R5 | RTO считается от RTT по алгоритму RFC 6298 (SRTT/RTTVAR), без лавины ретрансмитов | метрики симулятора |
| R6 | Таймауты, keepalive, корректный disconnect с причиной | сценарные тесты |
| R7 | Детерминизм: один seed даёт одинаковый результат | тест-повтор |

### 2.3 Производительность

| ID | Критерий | Цель | Как проверяем |
|----|----------|------|---------------|
| P1 | Ноль аллокаций в steady state (send/recv/poll) | 0 alloc/тик | тест со счётчиком аллокаций (counting allocator) |
| P2 | Пропускная способность сервера | ≥ 64 клиента × 60 Гц × 1 КБ на одном ядре, CPU < 10 % | criterion + нагрузочный тест |
| P3 | Задержка, которую добавляет библиотека | < 50 мкс на пакет | бенч |
| P4 | Размер нативного бинаря | < 1 МБ на платформу (release, strip) | CI-отчёт |
| P5 | В C#-биндинге нет GC-аллокаций при отправке и приёме | 0 B/op | BenchmarkDotNet |

### 2.4 Безопасность и устойчивость

| ID | Критерий | Как проверяем |
|----|----------|---------------|
| S1 | Нет амплификации: ответ на неаутентифицированный пакет ≤ размера запроса | тест + fuzz |
| S2 | Handshake через challenge/cookie: сервер не выделяет состояние до подтверждения адреса | тест + нагрузочный тест флуда |
| S3 | Парсер не паникует и не выходит за границы на любых входных данных | `cargo fuzz` (отдельная цель на каждый парсер), в CI короткий прогон |
| S4 | Лимиты: число подключений, rate limit на handshake, размер буферов reliable | тесты |
| S5 | Опционально (feature-флаг): шифрование и аутентификация ChaCha20-Poly1305, цена около 16–24 байт на пакет | тесты + замер overhead |
| S6 | `unsafe` есть только в FFI-слое, с документированными инвариантами | ревью + `cargo geiger` |

### 2.5 Платформы и интеграция

| ID | Критерий | Как проверяем |
|----|----------|---------------|
| X1 | Сборка под все целевые платформы из CI | матрица GitHub Actions, артефакты |
| X2 | C ABI стабилен, заголовок `.h` генерируется через cbindgen | CI проверяет diff заголовка |

| X7 | Unity sample (отдельная папка, только потребляет пакет) работает на Windows, macOS, Android и iOS против Linux-сервера | ручной чек-лист |

## 3. Архитектура

```
crates/
  netlib-core     # sans-IO: состояния соединений, каналы, ack, фрагментация, формат провода. no_std + alloc
  netlib-bits     # BitWriter/BitReader, varint, квантование, smallest-three, дельта-хелперы
  netlib          # std-драйвер: UdpSocket (non-blocking), Manager::poll(), время
  netlib-sim      # сетевой эмулятор (потери, задержка, джиттер, дубли, reorder, лимит полосы) для тестов
  netlib-ffi      # C ABI (cdylib + staticlib), cbindgen
  netlib-snapshot # [опционально, M7] снапшоты + дельта относительно последнего подтверждённого, redundant inputs, синхронизация тиков
bindings/dotnet   # NetLib.Native (.NET Standard 2.1), P/Invoke, Span-API, без Unity
examples/         # echo-сервер, консольный клиент, нагрузочный бот
unity-sample/     # отдельный Unity-проект: только потребитель, библиотека от него не зависит
fuzz/             # цели cargo-fuzz
```

Ключевые решения:

- **Sans-IO ядро.** В ядро передаются входящие байты и текущее время, оно возвращает исходящие пакеты и события. Сокеты и потоки живут только в драйвере. Отсюда детерминированные тесты и симулятор.
- **Poll-модель.** `manager.poll(now)` разбирает входящие пакеты в заранее выделенный буфер событий. Нет колбэков, нет фоновых потоков по умолчанию. Это проще для IL2CPP и для серверного тика.
- **Формат провода**, предварительно:
  - 1 байт типа и флагов;
  - [seq u16];
  - [ack u16 + ack-битмаска varint/u16..u32, только если флаг установлен];
  - сообщения: `[channel+flags 1 байт][len varint][payload]`, а для reliable ещё `[msg seq u16]`;
  - для одиночного сообщения длина не пишется, её даёт размер датаграммы.
- **MTU** по умолчанию 1200: безопасно для IPv6 и мобильных сетей. Опционально MTU discovery, как в LiteNetLib.

## 4. Как работаем интерактивно

Каждая веха устроена одинаково:

1. Короткий дизайн-апдейт (что делаем, какие решения).
2. Реализация в ветке `claude/udp-fps-sync-lib-4qvtv0`.
3. Автоматический отчёт `cargo xtask report`: таблица критериев этой вехи с отметкой ✅/❌ и цифрами (байты, аллокации, CPU, процент доставки).
4. Демо-команда, которую можно запустить самому, например `cargo run --example sim -- --loss 10 --latency 100`.
5. **Гейт аппрува**: ты смотришь отчёт и демо, после этого переходим к следующей вехе.

| Веха | Содержимое | Критерии | Демо |
|------|------------|----------|------|
| **M0** | Ответы на открытые вопросы (раздел 5), фиксация `WIRE_FORMAT.md` v0 | — | документ |
| **M1** | Workspace, CI (fmt / clippy / test / deny), sans-IO ядро: handshake с challenge, keepalive, timeout, disconnect; симулятор; std-драйвер | R6, R7, S1, S2, Q1 | echo-сервер и клиент на localhost; симулятор с потерями |
| **M2** | Каналы и все режимы доставки, ack-битмаска, RTO по RTT, склейка сообщений, фрагментация, пул буферов | R1–R5, B1–B5, P1 | `sim` с 20 % потерь + отчёт по байтам |
| **M3** | `netlib-bits`: bit-packing, квантование, smallest-three, дельта | B6 | пример «состояние 64 игроков в одном пакете» с размером в байтах |
| **M4** | FFI + cbindgen + .NET-биндинг, консольный C#-клиент против Rust-сервера, BenchmarkDotNet | X2, X3, X4 (частично), P5 | `dotnet run` клиент ↔ Rust-сервер |
| **M5** | Кросс-сборка для 5 платформ в CI, упаковка (Unity-пакет как набор нативных плагинов + .NET dll), Unity sample | X1, X4, X7, P4 | Unity-сцена: кубики-игроки двигаются через Linux-сервер |
| **M6** | Харденинг: fuzz, rate limit, лимиты, IPv6 / NAT64, смена сети, опциональное шифрование, soak 24 ч, нагрузочный тест | S3–S6, X5, X6, P2, P3 | нагрузочный бот: 64–256 клиентов |
| **M7** *(опц.)* | Слой снапшотов: дельта относительно последнего подтверждённого снапшота, redundant inputs, синхронизация серверного тика и часов | B4, B6 на реальном сценарии | FPS-подобная демка: 64 игрока, 60 Гц |
| **M8** | Сравнительный бенч с LiteNetLib, документация, релиз 0.1.0 | B7, Q2–Q4 | итоговый отчёт |

## 5. Открытые вопросы к аппруву

1. **Границы:** только транспорт уровня LiteNetLib (M1–M6) или нужен и слой снапшотов/дельты/синхронизации тиков (M7)? Prediction, reconciliation и lag compensation я предлагаю оставить игре, потому что они зависят от игровой логики.
2. **Шифрование:** опциональный feature-флаг (по умолчанию выключен, 0 байт overhead) или обязательное?
3. **Нужны ли NAT punch-through и LAN discovery?** Для схемы «выделенный сервер на Linux» они обычно не нужны.
4. **Миграция соединения** при смене IP на мобилке: прозрачная, через токен в заголовке (+1–2 байта на пакет, либо только в пакетах после смены адреса), или достаточно быстрого переподключения?
5. **Масштаб:** сколько игроков на сервер и какой tick rate (например 64 игрока × 60 Гц)? От этого зависят бенчмарки P2.
6. **Лицензия:** MIT/Apache-2.0?
7. **Минимальные версии:** Unity 2021.3 LTS или 2022 LTS+? .NET Standard 2.1 подходит?
