# Wire format v0

Документ описывает, как байты лежат в UDP-датаграмме.
До релиза 0.1.0 формат может меняться. Номер версии формата передаётся в `CONNECT_REQUEST`, и при несовпадении соединение отклоняется.

## Общие правила

- Все многобайтные целые записываются в **little-endian**.
- `varint` — unsigned LEB128: по 7 бит в байте, старший бит означает «есть продолжение». Значения 0–127 занимают 1 байт, 128–16383 — 2 байта.
- `u16` номера последовательностей сравниваются с учётом переполнения: `a` новее `b`, если `(a - b) mod 2^16` лежит в `1..32768`.
- Максимальный размер датаграммы равен `Config::mtu` (по умолчанию 1200 байт UDP payload). Получатель отбрасывает датаграммы больше `mtu`.
- Байт 0 любой датаграммы: младшие 4 бита — **тип пакета**, старшие 4 — **флаги**. Флаги есть только у `DATA`, у остальных типов они равны 0.

| Тип | Значение | Направление |
|-----|----------|-------------|
| `DATA` | 0 | оба |
| `CONNECT_REQUEST` | 1 | клиент → сервер |
| `CHALLENGE` | 2 | сервер → клиент |
| `CHALLENGE_RESPONSE` | 3 | клиент → сервер |
| `ACCEPT` | 4 | сервер → клиент |
| `REJECT` | 5 | сервер → клиент |
| `DISCONNECT` | 6 | оба |
| 7–15 | зарезервировано (MTU probe, миграция) | — |

Пакет неизвестного типа или с некорректной структурой молча отбрасывается.

## Handshake

```
клиент                                   сервер
  CONNECT_REQUEST (32 байта) ─────────────▶   состояния не создаёт
                         ◀─────────────── CHALLENGE (21 байт, stateless cookie)
  CHALLENGE_RESPONSE + connect data ──────▶   cookie валиден → pending peer → событие ConnectRequest
                         ◀─────────────── ACCEPT (21 байт) | REJECT
  DATA ◀────────────────────────────────▶ DATA
```

Защита от амплификации (S1): пока адрес клиента не подтверждён cookie, сервер отвечает пакетом **не больше** входящего.
`CONNECT_REQUEST` дополняется нулями до 32 байт, а `CHALLENGE` (21 байт) и ранний `REJECT` (11 байт) меньше него.

Сервер не хранит состояние до подтверждения адреса (S2). Cookie — это MAC, вычисленный SipHash-2-4 по 128-битному секрету сервера, поэтому его можно проверить, ничего не запоминая.

### CONNECT_REQUEST (1)

| Поле | Тип | Описание |
|------|-----|----------|
| type | u8 = 0x01 | |
| protocol_id | u32 | идентификатор приложения; чужой протокол молча отбрасывается |
| version | u16 | версия формата провода (сейчас 0) |
| nonce | u64 | случайное значение клиента, связывает все пакеты handshake |
| padding | нули до 32 байт | датаграмма короче 32 байт отбрасывается |

Клиент повторяет пакет каждые `connect_retry` (250 мс) до получения `CHALLENGE` или до `connect_timeout` (5 с).

### CHALLENGE (2)

| Поле | Тип | Описание |
|------|-----|----------|
| type | u8 = 0x02 | |
| nonce | u64 | эхо nonce клиента |
| timestamp | u32 | секунды по часам сервера (с момента старта менеджера) |
| mac | u64 | `SipHash24(secret, addr ‖ nonce ‖ timestamp ‖ protocol_id)` |

Длина 21 байт.

### CHALLENGE_RESPONSE (3)

| Поле | Тип | Описание |
|------|-----|----------|
| type | u8 = 0x03 | |
| nonce | u64 | |
| timestamp | u32 | из `CHALLENGE` |
| mac | u64 | из `CHALLENGE` |
| data_len | varint | ≤ `Config::max_connect_data` (по умолчанию 256) |
| data | bytes | данные приложения, например ключ подключения или токен авторизации |

Сервер принимает cookie, если MAC совпадает и `now_secs - timestamp ≤ cookie_lifetime` (10 с).
Кодирование адреса: для IPv4 это 1 байт `4`, 4 байта адреса и u16 порт; для IPv6 — 1 байт `6`, 16 байт адреса и u16 порт.

Что делает сервер с валидным ответом:

- для адреса нет пира: создаёт pending peer и генерирует событие `ConnectRequest`. Приложение вызывает `accept` или `reject`;
- для адреса есть pending peer с тем же nonce: игнорирует ответ, решение ещё не принято;
- для адреса есть connected peer с тем же nonce: отправляет `ACCEPT` повторно, первый потерялся;
- для адреса есть пир с другим nonce: клиент перезапустился. Старый пир удаляется с причиной `Reconnected`, создаётся новый.

Клиент повторяет `CHALLENGE_RESPONSE` каждые `connect_retry`, пока не получит `ACCEPT` или `REJECT`.

### ACCEPT (4)

| Поле | Тип | Описание |
|------|-----|----------|
| type | u8 = 0x04 | |
| nonce | u64 | |
| conn_id | u32 | случайный ненулевой идентификатор соединения |
| session_key | u64 | случайный ключ сессии; используется миграцией (M4) |

Длина 21 байт.

### REJECT (5)

| Поле | Тип | Описание |
|------|-----|----------|
| type | u8 = 0x05 | |
| nonce | u64 | |
| reason | u8 | `0` — отказ приложения, `1` — сервер полон, `2` — несовпадение версии |
| data_len | varint | |
| data | bytes | только при reason = 0 |

Ответы с reason 1 и 2 приходят на `CONNECT_REQUEST`, до проверки адреса, и всегда без данных: 11 байт < 32.

### DISCONNECT (6)

| Поле | Тип | Описание |
|------|-----|----------|
| type | u8 = 0x06 | |
| conn_id | u32 | должен совпадать с соединением, иначе пакет игнорируется |
| data_len | varint | |
| data | bytes | данные приложения |

Отправляется двумя копиями подряд, подтверждения не требует.
Если обе копии потеряются, вторая сторона закроет соединение по таймауту.

## DATA (0)

```
byte 0     [flags:4][type=0:4]
u16        seq                          — номер пакета соединения
если ACK:
  u16      ack                          — наибольший полученный seq
  u16      ack_bits                     — бит i = получен пакет ack-1-i
  u8       ack_delay                    — сколько получатель держал подтверждение пакета ack
blocks…                                 — до конца датаграммы
```

Флаги байта 0:

| Бит | Маска | Имя | Значение |
|-----|-------|-----|----------|
| 4 | 0x10 | ACK | есть блок подтверждений |
| 5 | 0x20 | PING | пакет требует подтверждения, даже если в нём нет reliable-данных (keepalive, замер RTT) |
| 6 | 0x40 | — | зарезервировано (миграция, M4) |
| 7 | 0x80 | — | зарезервировано (шифрование) |

Заголовок занимает **3 байта** без ACK (критерий B1) и **8 байт** с ACK (B2).

### Подтверждения

- Подтверждения работают на уровне пакетов, как у Glenn Fiedler: каждый получатель держит окно из 17 последних номеров (`ack` + 16 бит).
  Одно и то же подтверждение повторяется во всех исходящих пакетах, пока пакет не выпадет из окна, так что потеря одного пакета с ack ничего не ломает.
- Отправитель хранит, какие reliable-сообщения лежали в пакете `seq`. Подтверждение пакета подтверждает их все, а потеря пакета ставит их на ретрансмит (M2).
- **Ack-eliciting** — пакет с reliable-данными или флагом PING. На него получатель обязан ответить подтверждением.
  Если в ближайшем `flush()` есть данные, ack уходит в них (piggyback). Если данных нет, отправляется отдельный пакет из одного заголовка (8 байт), не ack-eliciting.
- Пакеты только с unreliable-данными подтверждения не требуют. Ack в них кладётся, если есть что подтверждать: новые полученные пакеты или текущее окно отправлено меньше трёх раз.
- **Дубли** отбрасываются по окну полученных seq (256 номеров). Пакеты старше окна тоже отбрасываются.
- **PING** ставится на исходящий пакет не реже `ping_interval` (1 с), поэтому RTT обновляется и при одностороннем unreliable-потоке. Флаг ничего не стоит: он живёт в байте 0.
  На PING получатель отвечает подтверждением **сразу**, не дожидаясь `flush()`, но не чаще раза в `ping_interval / 4`.

### RTT и ack_delay

Отправитель хранит время отправки каждого пакета. Когда приходит подтверждение, в котором наибольший `ack` подтверждён впервые, получается сэмпл:

```
latest_rtt = now - send_time(ack)
ack_delay  = decode(ack_delay)  — сколько получатель держал подтверждение
```

`ack_delay` — время от приёма пакета с наибольшим seq до отправки пакета с подтверждением. Кодируется одним байтом и округляется **вниз**, поэтому задержка никогда не завышается:

| Байт | Задержка | Шаг |
|------|----------|-----|
| 0–127 | 0–31,75 мс | 250 мкс |
| 128–255 | 32–159 мс | 1 мс (больше 159 мс — насыщение) |

Учёт задержки повторяет защиту RFC 9002 (QUIC) §5.3:

```
min_rtt      = min(min_rtt, latest_rtt)                      — только «сырые» сэмплы
ack_delay    = min(ack_delay, max_ack_delay)                 — Config::max_ack_delay, по умолчанию 100 мс
adjusted_rtt = max(latest_rtt - ack_delay, min_rtt)
```

- `peer_rtt` — сглаженный (RFC 6298) `adjusted_rtt`, то есть сетевой RTT без задержки на стороне получателя. Он не зависит от частоты тиков или FPS удалённой стороны.
- Таймер повторной отправки (RTO) считается по сглаженному `latest_rtt`: отправитель реально ждёт столько, задержка подтверждения включена.
- **Защита от неправдивого `ack_delay`.** Пир может сообщить завышенную задержку, чтобы занизить свой пинг. `adjusted_rtt` не опускается ниже `min_rtt` — минимального сырого сэмпла, а сырой сэмпл не может быть меньше реального RTT. Немедленные ответы на PING регулярно дают сэмплы почти без задержки, так что честный `min_rtt` близок к реальному RTT.
  Итог: занизить пинг ниже реального сетевого RTT нельзя, а завысить — можно и так, просто задерживая все пакеты.
- **Отличие от RFC 9002:** при `latest_rtt < min_rtt + ack_delay` RFC оставляет сырой сэмпл, а мы обрезаем результат до `min_rtt`. Гарантия та же, но округление `ack_delay` не выбрасывает поправку целиком.

### Повторная отправка (reliable)

- **Единица учёта** — reliable-сообщение или один его фрагмент. Отправитель помнит, в каком пакете единица ушла последний раз. Подтверждение любого пакета с этой единицей подтверждает её.
- **Потеря по порогу пакетов (RFC 9002):** пакет считается потерянным, когда подтверждён пакет, отправленный на 3 и более позже, а этот так и не подтверждён. Его единицы ставятся на повторную отправку в ближайшем `flush()`.
  Если единицу уже отправили заново в более позднем пакете, сообщение о потере старого пакета её не трогает.
- **Потеря по таймауту:** единица без подтверждения дольше `RTO × 2^min(retries, 3)` (не больше `max_rto`) отправляется заново.
  RTO считается по RFC 6298 из полного времени до прихода подтверждения. Экспоненциальный backoff не даёт устроить шторм повторных отправок при обрыве связи.
- **Окно:** одновременно в полёте не больше 1024 сообщений на канал. Получатель принимает номера в окне `[recv_next, recv_next + 1024)`.
  Более новые отбрасываются, отправитель повторит их позже. Более старые — дубликаты.
- **Очередь:** `send` возвращает `QueueFull`, когда `max_reliable_queue` сообщений канала (по умолчанию 4096) ждут подтверждения. `ReliableSequenced` хранит только последнее сообщение: новое вытесняет все предыдущие, и они больше не отправляются.
- **Фрагментация:** сообщение длиннее `mtu − 15` байт передаётся кусками-диапазонами, до `max_reliable_message` (по умолчанию 64 КиБ, максимум 16 МиБ).
  Кусок короче 64 байт отрезается только как последний. Получатель собирает куски в любом порядке, перекрытия допустимы.
  Ограничения: размер сообщения не больше `max_reliable_message`, суммарно недособранных данных на канал не больше `4 × max_reliable_message`.

### Блоки сообщений

Сообщения группируются в **блоки по каналу**. Благодаря этому много маленьких сообщений одного канала (например, 63 состояния игроков) стоят по 1 байту накладных расходов каждое.

```
block header (u8): [count:3][tail:1][channel:4]
  channel  0..15
  tail     1 = это последний блок в пакете, и у его последнего сообщения нет поля len
           (длина = остаток датаграммы)
  count    1..7 — число сообщений; 0 = далее varint count (≥ 8)
если канал reliable (ReliableUnordered / ReliableOrdered / ReliableSequenced):
  u16      base_seq
messages × count
```

Сообщение unreliable-канала (`Unreliable`, `UnreliableSequenced`):

```
len      varint        (нет у последнего сообщения tail-блока)
payload  len байт
```

Сообщение reliable-канала:

```
len      varint        (нет у последнего сообщения tail-блока)
tag      varint        = (delta << 1) | frag
                         delta = seq - prev_seq (mod 2^16), prev_seq сначала равен base_seq
                         сообщения в блоке отсортированы по seq, поэтому delta ≥ 0
если frag = 1:
  total    varint      — полная длина сообщения
  offset   varint      — смещение этого куска; offset + len ≤ total
payload  len байт
```

`UnreliableSequenced` не хранит своего номера: порядок определяется по `seq` пакета.
Сообщение отбрасывается, если в этом канале уже доставлено сообщение из более нового пакета.
Ретрансмитов у unreliable нет, поэтому порядок пакетов совпадает с порядком отправки.

Фрагментация доступна только reliable-каналам. Все куски одного сообщения делят его `seq`, и в окне упорядочивания сообщение занимает один номер.
Кусок задаётся диапазоном байт, а не номером, поэтому планировщик режет его под свободное место в пакете. Потерянный кусок при повторной отправке можно разрезать заново.

### Накладные расходы

| Что | Байт |
|-----|------|
| заголовок пакета (без / с ACK) | 3 / 8 |
| заголовок блока (≤ 7 / ≥ 8 сообщений) | 1 / 2 |
| `base_seq` reliable-блока | 2 |
| unreliable-сообщение, len < 128 | 1 (0, если последнее в tail-блоке) |
| unreliable-сообщение, len 128..16383 | 2 |
| reliable-сообщение (len < 128, delta < 64) | 2 |

Пример: 20 unreliable-сообщений по 40 байт в одном канале.
3 + 5 (ACK) + 2 (блок) + 19 × 1 (len) = **29 байт** накладных на 800 байт данных.
Для сравнения, в LiteNetLib это 1 + 20 × (2 len + 1 property) = 61 байт без ack.

## Планировщик (`flush`)

1. **Кандидаты.** Unreliable-сообщения в очереди. Для reliable — потерянные и ещё не отправленные диапазоны сообщений в окне.
   Unreliable с истёкшим TTL выбрасываются. Reliable-диапазоны без подтверждения дольше RTO с backoff считаются потерянными.
2. **Эффективный приоритет** = базовый (канал или `SendOptions::priority`) + `(255 − базовый) × ожидание / starvation_time`.
   Через `starvation_time` (500 мс) любое сообщение получает приоритет 255. При равенстве первым идёт более старое.
3. **Отбор:** кандидаты по убыванию эффективного приоритета, пока не кончится бюджет (`Config::bandwidth`, token bucket, запас 100 мс).
   Подтверждения и PING отправляются всегда, даже вне бюджета.
4. **Раскладка:** отобранное раскладывается по пакетам методом best-fit decreasing, куски фрагментированных сообщений заполняют оставшиеся дыры.
   Все пакеты одного `flush` уходят одновременно, поэтому порядок внутри `flush` на приоритеты не влияет.
5. **После отправки:** в `UnreliableSequenced` неотправленные сообщения старше отправленного выбрасываются как устаревшие.
   С `replace_key` новое unreliable-сообщение заменяет неотправленное старое с тем же ключом.

Гарантии и их условия:

- **Сообщение с низким приоритетом уходит не позже чем через `starvation_time`**, если поток с приоритетом 255 не превышает бюджет.
  Часто обновляемое состояние (позиции) стоит отправлять с `replace_key`, тогда очередь не копит устаревшие версии.
- **Высокий приоритет вытесняет низкий** в пределах `starvation_time`. Чтобы при постоянной перегрузке низкий приоритет никогда не вытеснял высокий, задайте ему TTL меньше `starvation_time`: такие сообщения выбрасываются раньше, чем успевают «состариться».
- **`UnreliableSequenced`:** сообщения из разных `flush` доставляются в порядке отправки. Внутри одного `flush` порядок не гарантирован.

## Состояния и таймеры (по умолчанию)

| Параметр | Значение |
|----------|----------|
| `connect_retry` | 250 мс |
| `connect_timeout` | 5 с |
| `cookie_lifetime` | 10 с |
| `starvation_time` | 500 мс: за это время любое ожидающее сообщение получает приоритет 255 |
| `bandwidth` | нет: бюджет полосы на пира, байт/с |
| `max_ack_delay` | 100 мс: больше этой задержки из RTT не вычитается |
| `ping_interval` | 1 с: PING-флаг на исходящем пакете; если за интервал ничего не отправлено, уходит пустой DATA с PING (keepalive) |
| `timeout` | 10 с без входящих пакетов → `Disconnected { reason: Timeout }` |
